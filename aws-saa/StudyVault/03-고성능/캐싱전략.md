# 캐싱 전략

## 캐싱 계층별 서비스

```
사용자
  ↓
CloudFront (CDN 캐시, 엣지)
  ↓
ALB
  ↓
애플리케이션 서버
  ↓
ElastiCache / DAX (DB 앞단 캐시)
  ↓
데이터베이스 (RDS, DynamoDB)
```

## 캐싱 패턴

### Lazy Loading (지연 로딩) - 가장 일반적
```
1. 캐시 조회 → 캐시 히트 → 반환 (빠름)
2. 캐시 미스 → DB 조회 → 캐시 저장 → 반환
```
- 장점: 실제 사용 데이터만 캐시
- 단점: 첫 요청 느림 (3 hop), 오래된 데이터 가능성

### Write Through (즉시 쓰기)
```
1. DB 쓰기
2. 동시에 캐시 업데이트
```
- 장점: 항상 최신 데이터
- 단점: 쓰기 지연, 불필요한 데이터도 캐시

### Cache Aside (앱 제어)
- 앱이 직접 캐시와 DB를 관리
- Lazy Loading과 유사하나 앱이 전략 결정

## 세션 스토어 (Session Store)

```
사용자 → 여러 EC2 인스턴스 (ALB 분산)
              ↓
        ElastiCache (공유 세션 저장소)
```

> [!important] 세션 고착 vs 공유 세션
> 스티키 세션: 특정 EC2에 묶임 → 장애 시 세션 손실
> ElastiCache 세션: 모든 EC2 공유 → 장애 시 세션 유지

## 서비스별 캐싱 적용

| 서비스 | 캐싱 방법 | 특징 |
|--------|-----------|------|
| RDS | ElastiCache (Redis) | 읽기 쿼리 캐시 |
| DynamoDB | DAX | API 변경 없음, 마이크로초 응답 |
| API 응답 | API Gateway 캐시 | 특정 엔드포인트 결과 캐시 |
| 정적 콘텐츠 | CloudFront | 글로벌 엣지 캐시 |

## CloudFront 캐싱 최적화

### Cache Key 설계
- 기본: URL만
- 커스텀: URL + 헤더 + 쿠키 + 쿼리스트링
- 캐시 키에 포함될수록 캐시 효율↓ (다양한 캐시 항목 생성)

> [!tip] 캐시 적중률(Hit Rate) 향상
> 불필요한 헤더/쿠키는 캐시 키에서 제외
> 정적 vs 동적 콘텐츠 배포 분리

## 시험 함정

> [!warning]- 캐싱 함정
> - **DAX**: 읽기 성능용, 쓰기 성능 향상 아님
> - **ElastiCache Redis**: Multi-AZ 지원, Memcached는 지원 안 함
> - **API Gateway 캐시**: TTL 설정 필수 (기본 300초)
> - **Lazy Loading**: 캐시 미스 시 오래된 데이터 문제 → TTL로 해결
