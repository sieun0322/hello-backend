# 메시징 & 이벤트 처리

## SQS (Simple Queue Service)

### 유형 비교
| 항목 | Standard Queue | FIFO Queue |
|------|----------------|------------|
| 순서 | 보장 안 됨 (최선) | 엄격한 순서 보장 |
| 처리량 | 무제한 | 초당 300 메시지 (배치 시 3,000) |
| 중복 | 가능 | 정확히 한 번 처리 |
| 용도 | 고처리량, 순서 무관 | 주문 처리, 금융 거래 |

### 핵심 개념
```
가시성 타임아웃 (Visibility Timeout)
→ 메시지 처리 중 다른 소비자에게 안 보임 (기본 30초)
→ 처리 실패 시 타임아웃 후 다시 가시화

DLQ (Dead Letter Queue)
→ 최대 수신 횟수 초과 메시지 → DLQ로 이동 → 분석/재처리
```

> [!tip] Long Polling vs Short Polling
> Short Polling: 즉시 응답 (메시지 없어도), 비용 높음
> Long Polling: 최대 20초 대기, 비용 효율적 (권장)

### SQS 확장 클라이언트
- SQS 메시지 최대 크기: **256KB**
- 더 큰 페이로드: S3에 저장 + SQS에 S3 참조 전송

## SNS (Simple Notification Service)

### Pub/Sub 패턴
```
Publisher → SNS Topic → 구독자 1 (Lambda)
                     → 구독자 2 (SQS)
                     → 구독자 3 (Email)
                     → 구독자 4 (HTTP/HTTPS)
```

### SNS + SQS Fanout 패턴
```
이벤트 → SNS
          ├── SQS 1 → 처리 워커 A
          └── SQS 2 → 처리 워커 B
```
> [!tip] Fanout 용도
> S3 이벤트를 여러 SQS 큐에 동시 전달 (S3는 단일 이벤트 대상)

### SNS FIFO
- SNS FIFO → SQS FIFO만 구독 가능
- 순서 보장 + 중복 제거

## Kinesis

### 서비스 비교
| 서비스 | 특징 | 용도 |
|--------|------|------|
| Kinesis Data Streams | 실시간 스트림, 샤드 기반 | 커스텀 처리, 낮은 지연 |
| Kinesis Firehose | 완전 관리형, 변환 후 저장 | S3/Redshift/OpenSearch 로드 |
| Kinesis Data Analytics | SQL/Flink로 실시간 분석 | 실시간 집계, 이상 탐지 |

### Kinesis Data Streams
```
Producer → 샤드 (Shard)
              ↓
          Consumer (Lambda, Kinesis Analytics)
```
- 샤드당: 1MB/s 입력, 2MB/s 출력
- 보관: 기본 24시간, 최대 365일
- 소비자 수에 따라 샤드 확장 (리샤딩)

> [!important] Kinesis vs SQS
> Kinesis: **실시간 스트리밍**, 순서 보장 (샤드 내), 여러 소비자
> SQS: **큐**, 메시지 처리 후 삭제, 단일 소비자 그룹

## Amazon MSK (Managed Streaming for Kafka)

- 완전 관리형 Apache Kafka
- Kinesis 대안 (기존 Kafka 워크로드 이전)
- MSK Connect: Kafka 커넥터 관리

## 시험 함정

> [!warning]- 메시징 함정
> - **SQS 가시성 타임아웃**: 처리 시간보다 길게 설정
> - **SNS 직접 Lambda**: SQS 버퍼 없이 → Lambda 동시성 폭발 가능
> - **Kinesis 샤드**: 핫 샤드 → 파티션 키 분산 설계
> - **Firehose**: 최소 60초 버퍼 → 실시간 아님 (near-real-time)
> - **SQS DLQ**: 최대 수신 횟수 초과 후 이동 (즉시 이동 아님)
